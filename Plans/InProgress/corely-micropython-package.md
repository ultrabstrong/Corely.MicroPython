# Plan: Corely.MicroPython as a Package of Its Own

## Context

`corely/` was built to be lifted out ("self-contained, so it can be lifted
into its own repo"). Now it gets a repository, a version, releases and
documentation, the way Corely.Common and the other Corely libraries have
them, and this repository consumes it like a package instead of owning it.

**MicroPython's NuGet is `mip`.** There is no central registry for third
party packages: a public GitHub repository with a `package.json` is the
feed, and a git tag is the version.

	mpremote mip install github:ultrabstrong/Corely.MicroPython@Corely.MicroPython-v1.0.0

`mip` reads `package.json`, fetches the listed files at that tag, and installs
the listed dependencies from micropython-lib's index. The repository is
public for that reason: a board has no GitHub login.

## Decisions (from the owner)

- **Name:** `Corely.MicroPython`. The import name stays `corely`.
- **Public**, like the other Corely repositories.
- **Consumed as a pinned release with a local override:** this repository
  vendors a released copy at `vendor/corely/` (a `PackageReference`), and
  `deploy.py --corely ../Corely.MicroPython` deploys a working copy instead
  while both are being changed (a `ProjectReference`).

## The New Repository

Mirrors Corely.Common:

| Corely.Common | Corely.MicroPython |
|---|---|
| `<Version>` in the csproj | `"version"` in `package.json` |
| tag `Corely.Common-v<Version>` | tag `Corely.MicroPython-v<Version>` |
| `ci.yml`: build and test every push | `ci.yml`: host tests, plus every module compiled with `mpy-cross` (catches syntax MicroPython lacks) |
| `release.yml`: pack, push to NuGet | `release.yml`: check the tag against `package.json`, test, build a `.mpy` bundle, publish a GitHub release |
| `scripts/release-package.sh` | the same, reading `package.json` |
| `scripts/check-package-versions.sh` | the same |
| `Docs/` per the documentation style guide | split from today's `corely/README.md`, one page per module |
| README, CONTRIBUTING, LICENSE (MIT), CLAUDE.md, Plans | the same |

- **History kept:** `corely/` and `tests/` are carried over with their git
  history (`git filter-repo`).
- **`package.json` lists every module** and is generated by a script; CI
  fails if it is out of date with `corely/`.
- **Dependencies:** `logging`, `aioble`, `aiohttp` from micropython-lib.
  The sensor drivers are optional (only `corely.sensors` imports them, and
  only when a sensor is opened), so they are a second package file,
  `sensors.json`, pointing at the pinned upstream files this repository
  vendors today. Each was confirmed identical to its upstream.
- **Release assets:** the `.mpy` bundle (smaller and faster to import, for
  copying by hand) and the source.
- **First version 1.0.0**, released by tag once CI is green.

## This Repository Afterwards

- `corely/` and `tests/` go; `vendor/corely/` holds the released copy.
- `scripts/update_corely.py <version>` refreshes `vendor/corely/` from a
  release. `vendor/README.md` records the version, as for every package.
- `deploy.py` and `release.py` take Corely from `vendor/` like any package,
  or from `--corely <path>`.
- `pico2/tests` no longer import the library's test harness.
- CLAUDE.md: the library half moves to the new repository's CLAUDE.md; this
  one says where Corely comes from and how to co-develop.

## Out of Scope

- PyPI. `mip` cannot install from it, so it would only be a listing.
- Getting into micropython-lib's own index (a pull request to them, later).
- Rewriting existing code comments to the docs' no-dash rule; new docs follow
  it.

## Verification

1. CI green on the new repository: host tests and the `mpy-cross` compile.
2. The release workflow publishes `Corely.MicroPython-v1.0.0` with assets.
3. On the Pico: `mip install` from GitHub at that tag into a test folder
   installs every module and its dependencies.
4. This repository: both test suites pass from the vendored copy, and the
   demos deploy and run from it.
